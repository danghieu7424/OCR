# FerriteDB Android device evaluation — 2026-11-17

## Device and scope

- Device: Samsung SM-J250F (`j2y18lte`), Android 7.1.1 (API 25), `armeabi-v7a`.
- Binaries were built with Android API 23 as the minimum platform (`cargo-ndk -P 23`).
- Rust target: `armv7-linux-androideabi`; built with `cargo-ndk 4.1.2`.
- The existing `deploy_android.bat` was already running. It was read only: this
  evaluation did not edit, execute, stop, or use its WBF binary, storage, or
  update paths.
- FerriteDB binaries and the example database were isolated under
  `/data/local/tmp/ferritedb-validation-20261117-1922`; commands ran as the
  Android `shell` user, not as the WBF service.
- All benchmark records were generated by FerriteDB examples. No reference
  dataset or WBF user data was used. The benchmark examples removed their
  generated database/WAL files on successful exit; the isolated test directory
  was removed after validation.
- Android's linker printed `unsupported flags DT_FLAGS_1=0x8000001` for the
  test and example executables. `llvm-readelf` identifies the flags as `NOW`
  and `PIE`; all executables continued and returned success. Keep these
  hardening flags rather than removing them just to silence the API 25 linker's
  compatibility warning.

## Workspace tests on device

Built the full test targets with:

```text
cargo ndk -t armeabi-v7a -P 23 test --workspace --no-run --locked
```

Each unique test executable was pushed to the isolated directory and run with
`--format terse --test-threads=1`.

| Test target | Passed | Failed |
|---|---:|---:|
| `ferrite-btree` | 23 | 0 |
| `ferrite-pager` | 28 | 0 |
| `ferrite-cache/tests/cache_consistency` | 5 | 0 |
| `ferrite-vdbe` | 2 | 0 |
| `ferrite-vdbe/tests/sql_execution` | 3 | 0 |
| `ferrite-vfs` | 9 | 0 |
| `ferritedb-core` | 13 | 0 |
| `ferritedb` facade | 2 | 0 |
| **Total** | **85** | **0** |

The cache consistency suite uses `InMemoryValkey`; it required no Redis or
Valkey service. The standalone `ferrite-cache` library target contains no
unit tests. The host workspace run additionally passed one facade doctest.

The `playback_history` example was run twice against the same device-local
database path. Both runs returned the same normalized media path and saved
position, verifying schema creation, reopen, and upsert on the Android OS VFS.
The media path was only a string; no media file was accessed.

## Performance and optimization

The `open_bench` and `database_bench` examples used 5,000 synthetic rows. The
baseline was one run before the CRC change; post-change values are the median
of three runs. Each `open_bench` run reports a median over 20 opens.

| Metric | Baseline | Post-change median | Change |
|---|---:|---:|---:|
| Checkpointed `Database::open` | 8,926 µs | 8,997 µs | +0.8% |
| WAL-backed `Database::open` (76 frames, 313,152 bytes) | 21,598 µs | 13,135 µs | -39.2% |
| Batch insert throughput | 2,910 rows/s | 2,970 rows/s | +2.1% |
| Point lookup throughput | 4,207 queries/s | 4,322 queries/s | +2.7% |
| **Total benchmark runs** | **1** | **3 (60 open samples per database state)** | — |

`open_bench` reports the median and mean duration for `Database::open`;
throughput is rows or point lookups divided by elapsed time. Change is
`(post-change / baseline - 1)`. The baseline consists of one run, so the
before/after comparison is indicative rather than a statistical guarantee.
Rows, benchmark arguments, Android device, and filesystem location were held
constant.

The measured change replaces the bit-at-a-time CRC32C implementation with a
compile-time lookup table and computes both frame checksum chains in one pass.
The WAL format and checksum values are unchanged; a regression test compares
page-sized results with the prior bitwise algorithm. A separate positional
I/O experiment showed no material device improvement and was reverted.

Exact release benchmark commands:

```text
cargo ndk -t armeabi-v7a -P 23 build --release --locked --example database_bench --example open_bench
open_bench 5000 20
database_bench 5000
```

## Limitations

- This validates one Android 7.1.1 device using `/data/local/tmp`, not an
  Android app process or its private sandbox.
- No real power-cut test was performed. Fault injection remains simulated by
  `SimVfs`; filesystem durability can vary by device and filesystem.
- Multi-process reader coordination remains unsupported.
- The result does not constitute a WBF backend integration or a remote CI run.
